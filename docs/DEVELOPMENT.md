# Разработка Sirin Music 2.0

Работа над следующей версией ведётся в `dev`. Стабильная ветка — `master`; изменения переносятся туда после проверки и решения о выпуске. Pull request следует направлять в `dev`.

## Состояние версии 2.0

Главная, профиль и настройки переработаны. Настройки разделены на оформление, хранилище и подключение; аккаунт, сервер, обновления и информация о приложении открываются отдельно. На широких экранах используются навигационная панель и адаптивные сетки.

Профиль поддерживает границы новизны, недельную статистику, настроения, скрытые записи и ссылки на радио. Главная предлагает запуск радио, передачу ссылки и обновление миксов. Вход доступен по QR, имени и паролю или токену. Добавлены синхронизация воспроизведения и фото артистов.

Управление аккаунтом и администраторами требует отдельной cookie-сессии через HTTPS. Возможности новых разделов зависят от серверного API; отсутствие поддержки и ошибки отображаются в соответствующем разделе. Подробнее о контрактах и ограничениях — ниже.

## Проверка изменений

```sh
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
```

Проверять навигацию, пересоздание Activity, подключение, компактные и широкие экраны. Воспроизведение и системное управление проверять на устройстве. Изменения интерфейса не должны нарушать серверную очередь, оценки и защиту учётных данных.

## Тестовые сборки и публикация

Текущий CI проверяет `master` и `dev`. Debug APK доступен в артефакте `sirin-music-debug`; при push в `dev` дополнительно собирается оптимизированный APK с подписью приложения.

Подготовленная версия — `2.0.0`, код версии — `3`. После push в `dev` CI сохранит подписанный APK в артефакте `sirin-music-2.0.0`. Старый тег `1.5-dev` остаётся в истории и в триггерах workflow; для текущей работы новый тег не создаётся. Тестовые артефакты не публикуются как GitHub Release и не предлагаются встроенной проверкой обновлений.

Версия 2.0 выпускается после завершения работ и проверки. Порядок подписи и публикации описан в [RELEASING.md](RELEASING.md).

## Уже реализованные механизмы

Следующие разделы описывают существующую реализацию, которую нужно сохранить при переработке экранов.

## Память и хранилище

Обложки используют ограниченный LRU-кеш: 64 МиБ на диске и до 24 МиБ в оперативной памяти (не более 10% доступной приложению heap). При уведомлении Android о нехватке памяти или уходе интерфейса в фон кеш в RAM очищается. Изображения, которые ещё отображаются на экране, могут оставаться в памяти до закрытия экрана.

В настройках показывается текущий размер дискового кеша и доступна кнопка очистки. Она удаляет кеш обложек в RAM и на диске; данные подключения, избранное на сервере и воспроизведение не затрагиваются. Отображаемые обложки могут кешироваться повторно при следующих запросах. Музыка на диск не сохраняется.

Размер «Приложение» в Android не равен размеру APK и не является размером кеша. Для release включены R8 и удаление неиспользуемых ресурсов. Размер установленных файлов и подготовленного Android кода зависит от устройства. Debug-сборки не уменьшаются R8.

## Оформление и большие экраны

Десять готовых палитр и свой цвет: оттенок, насыщенность, яркость или HEX. [MaterialKolor Color Utilities](https://github.com/jordond/MaterialKolor) строит полную светлую/тёмную схему с контрастным текстом. При включённых цветах из обоев используется системная схема; для выбора своего цвета этот переключатель нужно выключить.

На широких окнах используется навигационная панель сбоку, адаптивные сетки избранного, артистов, альбомов и плейлистов. В плеере от 840 dp управление и очередь располагаются в двух колонках с независимой прокруткой. Настройки, вход, профиль и тексты песен ограничены по ширине для удобного чтения.

## Оптимизация после первой dev-сборки

JSON декодируется в фоновом потоке. Поиск обрабатывает только открытую вкладку, с задержкой 200 мс при вводе; пустой запрос возвращает исходный список без копии. Сравнение текста не создаёт lowercase-копии метаданных каждого трека. Позиция воспроизведения больше не передаётся в библиотеку; оценки и доступность действий обновляются отдельно. Обложки в списках используют AsyncImage с общей подложкой вместо подкомпозиции. Завершённые фоновые задачи удаляются из реестра ViewModel, включая операции избранного с разными ID.

## Обновления приложения

В настройках есть кнопка «Проверить новую версию», открывающая отдельный экран обновлений и запускающая проверку по явному нажатию. Флажок «Проверять обновления при запуске приложения» по умолчанию выключен. При включении выполняется одна проверка за процесс приложения; возврат из фона, поворот и пересоздание Activity её не повторяют. Изменение флажка действует со следующего запуска процесса. Суточная проверка через WorkManager также по умолчанию выключена и включается отдельно. При выключенном переключателе периодическая задача отменяется; после включения первая фоновая проверка назначается через сутки. Оба механизма независимы, ручная проверка доступна при выключенных флажках. Разрешение Android на уведомления запрашивается отдельной кнопкой.

Клиент проверяет только стабильные GitHub Releases. Артефакты ветки `dev` и тег без Release не предлагаются; Сравнение учитывает числовые компоненты и prerelease. Загрузка начинается по кнопке, идёт потоково в один временный APK, ограничена 64 МиБ; проверяются размер, SHA-256 из метаданных GitHub, имя пакета, версия, совместимость Android и совпадение сертификатов установленного приложения. Системный установщик дополнительно проверяет APK и требует подтверждения пользователя. Debug-сборка не сможет обновиться APK с production-подписью.

Для установки используется FileProvider с доступом только к `cache/updates/`. Частичная загрузка удаляется при ошибке или отмене; завершённый APK хранится до установки или очистки устаревших файлов при запуске (сутки). Клиент GitHub отдельный и не содержит токен сервера musik.


## Профиль и подборки в 2.0rc0.2-dev

Главная предлагает поделиться серверной ссылкой на радио и обновить миксы. Обновление создаёт `mix_pack` на сервере; приложение ожидает завершения задания и перечитывает подборки. Для выполнения нужен работающий серверный воркер. Ожидание ограничено тремя минутами; выход из приложения не отменяет серверное задание.

Профиль получает счётчики вкуса (`n_positive`, `n_negative`), границы новизны и частых артистов из `/api/profile`; недельные показатели — из `/api/metrics/weekly`, фактическую новизну последнего набора — из `/api/metrics/recommendations`. Отсутствующие значения не заменяются демонстрационными числами. Ошибки отдельных разделов не скрывают остальные данные.

Настроения создаются и хранятся на сервере. Их включение относится к текущей сессии радио; несколько могут работать одновременно. Скрытые записи можно вернуть, публичные ссылки — создать, отправить через Android и отозвать. В отправляемой ссылке нет API-токена приложения. Настройки оформления, кеша, подключения и обновлений остаются на отдельном экране настроек.


## Вход 2.0rc0.5-dev

QR и ручной Bearer-токен сохраняются. Новый вход использует `/api/auth/token`: имя и пароль для аккаунтов либо только пароль для сервера с одним владельцем. Если получено несколько профилей, перед сохранением подключения выбирается профиль телефона. Пароль хранится только в памяти формы/незавершённого входа. Если выбран другой профиль, сервер выпускает отдельный токен; управление и отзыв токенов остаются в веб-интерфейсе сервера.

Проверка подключения использует `/api/auth/me` и поле `ok`, затем `/api/health`. Вход без токена доступен отдельной кнопкой только когда сервер явно подтвердил отключённую авторизацию. На старом сервере без `/api/auth/token` предлагается QR или ручной токен. Отсутствующий API не подменяется браузерным cookie-входом.


## Синхронизация и фото артистов 2.0rc0.5-dev

Состояние восстанавливается через `/api/playback/state` и живую `/api/now` на паузе, без повторного track_start. При запуске передаётся claim, при активном проигрывании состояние обновляется раз в5секунд; потеря владения ставит телефон на паузу. Пауза и перемотка сохраняются отдельно, постоянных запросов на паузе нет. При возвращении на экран приложение проверяет состояние приостановленного плеера.404 нового stateAPI отключает синхронизацию до смены подключения; сетевые ошибки не считаются отсутствием поддержки. Недоступная или изменившаяся сессия не восстанавливается под другим track_id.

Библиотека получает фото через `/api/artist-photos`. Изображения используют общий авторизованный Coil и существующие ограничения кеша; при ошибке остаётся обложка. Старый сервер с404 продолжает работать с обложками. Фото должны быть предварительно загружены на сервер — обновление его программы само по себе не заполняет новую таблицу фотографий.

### Настройки сервера в 2.0rc0.5-dev

Отдельная `ServerSettingsActivity` открывается из профиля и меню настроек. Использует `/api/settings` (GET/PUT), `/api/settings/dirs`, `/api/settings/external-ip` и `/api/settings/restart`. Выбор папки выполняется на сервере, не через Android Documents. Режимы LAN и Интернет оба слушают все интерфейсы; доступ извне зависит от туннеля/роутера. Перезапуск доступен только при `restart_supported=true`, требует подтверждения. Сохранение не запускает сканирование и не меняет подключение клиента. 403 для device token объясняет необходимость административного доступа через браузер.

Токен и QR только в памяти, не в savedInstanceState; DTO с секретами не data class. На экране установлен FLAG_SECURE, буфер обмена токена помечен sensitive. QR генерируется локально ZXing, в том же формате `musik://connect`, без дискового кеша. Внешний IP запрашивается только по нажатию. В Docker API может писать /app/.env без постоянного сохранения; интерфейс предупреждает о ручном перезапуске и конфигурации контейнера.

## 2.0rc0.7-dev: QR и аккаунты

Экран входа использует фирменную иконку Sirin. Сканер `ui.qr.QrScanActivity` использует Material 3, скруглённая камера, фонарик, запрос разрешения, выбор изображения через системный Photo Picker и ручная ссылка. Камера работает только при видимом экране; изображения декодируются с ограничением размера до2048. Результат совместим с ScanContract и проверяется ConnectLink; текст с токеном не пишется в savedInstanceState.

Отдельная `AccountActivity` доступна из профиля и настроек. Управление требует повторного входа по имени и паролю через HTTPS; пароль и сессионные cookie не сохраняются на диск. Собственный `AccountApi` не использует Bearer плеера: cookie ограничены точным origin, перенаправления запрещены, изменения отправляют CSRF. Сеанс сохраняется при повороте через ViewModel и закрывается при завершении Activity. Экран защищён FLAG_SECURE.

Поддерживаются смена пароля, создание/переименование/удаление профилей, выбор профиля сеанса управления и отдельное применение профиля к плееру через новый device token. Токены устройств: список, сроки, последнее использование, создание, перевыпуск, отзыв и QR. Старые device tokens автоматически не отзываются при смене профиля. Для администраторов доступны приглашения (email/срок, ссылка, список/отзыв) и пользователи (статус/права). Удаление профиля, отзыв/перевыпуск токена и изменение прав требуют подтверждения. Основной профиль и последний администратор дополнительно защищены сервером.

Новые токены и ссылки приглашений показываются только при выпуске, не восстанавливаются из savedInstanceState, sensitive clipboard. Выбор профиля в сеансе управления не меняет плеер без кнопки «Использовать профиль в приложении». Сканирование музыки эти экраны не запускают.
